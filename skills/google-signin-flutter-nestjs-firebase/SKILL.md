# Google Sign-In: Mobile + Vercel-hosted Node backend playbook

A working Google Sign-In flow has **five places** that must all agree on the same Web OAuth client ID and stay in sync. When sign-in fails, the symptom usually points at the wrong layer. This skill is the diagnosis tree for the common failures, with verification steps that work and instrumentation that catches each class of bug.

## The five points of agreement

| # | Where | What |
|---|---|---|
| 1 | Firebase Console → Project Settings → Web SDK config | The **Web OAuth client ID** (`<num>-<hash>.apps.googleusercontent.com`). Auto-created by Firebase. |
| 2 | Firebase Android app → SHA fingerprints | Three SHA-1s registered: **debug keystore**, **upload keystore**, **Play App Signing key**. |
| 3 | Mobile app build (`--dart-define` for Flutter, `expo-config-plugin`/`extra` for Expo) | Same Web Client ID baked into the build → passed to `GoogleSignIn` as `serverClientId` (Flutter) or `webClientId` (Expo). |
| 4 | Backend env (`GOOGLE_CLIENT_ID` on Vercel) | Same Web Client ID — used as `audience` in `OAuth2Client.verifyIdToken({ idToken, audience })`. |
| 5 | `google-services.json` (committed locally, gitignored, materialized in CI) | Generated by Firebase **after** all three SHA-1s are added; must be present at `android/app/google-services.json`. |

The flow:
1. App calls `GoogleSignIn.signIn()` → Google validates `(package_name, apk_sha1)` against the Firebase Android app → issues an `idToken` whose `aud` claim is the Web Client ID.
2. App POSTs `{idToken}` to backend `/auth/google`.
3. Backend `verifyIdToken({ idToken, audience: GOOGLE_CLIENT_ID })`. Google checks signature against Google's public keys; library checks `aud == audience`.
4. On success, backend issues its own JWT and returns it.

If any of (1–5) drifts, sign-in fails. The error you see depends on which one.

## Failure-mode → root-cause table

| Symptom (user-visible) | Where to look first | Most common root cause |
|---|---|---|
| `DEVELOPER_ERROR` / `ApiException 10` from the SDK before any backend call | Layer 2 + 5 | The currently-installed APK's SHA-1 isn't in Firebase. Also: missing `google-services.json` in build → app-gms plugin not applied. |
| Native chooser opens, account selected, then **silent return / no toast** | Layer 3 | `serverClientId` / `webClientId` is empty in the build (env not piped through). idToken comes back null → app gives up silently. |
| **HTTP 401** from `/auth/google` with `"Invalid Google idToken"` | Layer 4 | Backend `audience` (`GOOGLE_CLIENT_ID`) doesn't match the JWT's `aud`. **Often: env value has leading `"` and trailing `"` and/or literal `\n` — the paste-trap.** |
| **HTTP 401** with `"Google sign-in is not configured on the server"` | Layer 4 | Backend `GOOGLE_CLIENT_ID` env var is unset (or set on the wrong environment, e.g. Preview not Production). |
| **HTTP 500** with `"expiresIn should be a number..."` | Layer 4 | `JWT_EXPIRES_IN` env value has the same paste-trap (e.g. literal `30d\n`). |
| **HTTP 500** with `column "googleSub" does not exist` | Backend DB | Schema migration not applied. With `synchronize: false` in prod, you must run a DDL script. |
| Works in `flutter run` debug, fails on Play Store closed-testing | Layer 2 | Play App Signing SHA-1 not added to Firebase. Google re-signs every AAB on Play, so the SHA-1 of what the user actually installs differs from your upload key's. |

## The literal-`\n` env-paste trap (Vercel, Netlify, Render, et al.)

When values are pasted into a dashboard env-var input from a quoted source — Notion code blocks, Slack snippets, terminal output with line wrap — the surrounding `"..."` and a literal `\n` (backslash + n, **not** a real newline) often come along. The dashboard stores them verbatim. The lambda reads them verbatim. `OAuth2Client.verifyIdToken({ audience: '"...com\\n"' })` then fails to match the JWT's actual `aud`.

**Detection:**
```bash
vercel env pull .env.local --environment=production --yes
grep '^GOOGLE_CLIENT_ID=' .env.local | sed 's/^GOOGLE_CLIENT_ID=//' | xxd | head -3
```

If you see `22 ...` at the start (`"` opening quote) or `5c 6e 22 0a` near the end (`\n"` + line terminator from the file format), the value is poisoned.

The shell-parsed length should match what you expect. For a Web Client ID it's typically **72 chars** (`<project-number>-<32-char-hash>.apps.googleusercontent.com`). If `${#GOOGLE_CLIENT_ID}` is 75–76, you've got the trap.

**Fix (CLI, repeatable):**
```bash
# Remove the broken value
vercel env rm GOOGLE_CLIENT_ID production --yes

# Re-add via stdin with NO trailing newline
printf '%s' "<project-number>-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx.apps.googleusercontent.com" \
  | vercel env add GOOGLE_CLIENT_ID production

# Verify
vercel env pull .env.local --environment=production --yes
grep '^GOOGLE_CLIENT_ID=' .env.local | sed 's/^GOOGLE_CLIENT_ID=//' | xxd | head -3
# Expected: bytes 0..71 = the URL, then 0a (file line terminator). No 5c 6e. No leading/trailing 22.

# Redeploy — env changes don't refresh existing deployments
vercel deploy --prod --yes
```

`printf '%s'` is critical. `echo "value" | vercel env add` adds a trailing newline that becomes part of the stored value — recreating the trap.

## Vercel env updates DO NOT update active deployments

Changing an env var in the Vercel dashboard or CLI only affects **new** deployments. Existing lambdas keep using the env values they had at build time. After any env change, **always redeploy**:

```bash
vercel deploy --prod --yes
# or, in the dashboard: Deployments → Redeploy on the latest one
```

## When Vercel↔GitHub auto-deploy is broken

If `git push` doesn't produce a new Vercel deployment within ~30s:

1. Check the GitHub repo's **Settings → Webhooks** for the Vercel webhook. If it shows recent failures, reauthorize the Vercel GitHub integration (Vercel dashboard → Settings → Git).
2. Until that's fixed, deploy manually each push: `cd <project> && vercel deploy --prod --yes`.
3. Don't rely on `vercel rollback <url>` for cross-team aliases — it errors with "Deployment belongs to a different team" on personal-vs-org scope mismatch. Use the dashboard for rollback in that case.

## Schema migration gotcha (Vercel + Neon + TypeORM)

Vercel uses Neon's pgBouncer connection (pooled), which doesn't support TypeORM's `synchronize: true` for DDL operations. So `synchronize` is typically off in production, and adding a column to an entity (`@Column() googleSub?: string`) DOES NOT add it to the live DB on next deploy. Your sign-in then 500s with `column "googleSub" does not exist`.

**Pattern that works:** an idempotent `scripts/migrate.mjs` in the backend repo that runs raw `ALTER TABLE ... ADD COLUMN IF NOT EXISTS ...` against the **unpooled** URL.

```js
// scripts/migrate.mjs
import 'dotenv/config';
import pg from 'pg';
const c = new pg.Client({
  connectionString: process.env.DATABASE_URL_UNPOOLED ?? process.env.DATABASE_URL,
});
await c.connect();
for (const sql of [
  `ALTER TABLE users ADD COLUMN IF NOT EXISTS "googleSub" text`,
  `CREATE UNIQUE INDEX IF NOT EXISTS users_googlesub_uq ON users ("googleSub") WHERE "googleSub" IS NOT NULL`,
  `CREATE UNIQUE INDEX IF NOT EXISTS users_email_uq ON users (email) WHERE email IS NOT NULL`,
]) {
  console.log(sql);
  await c.query(sql);
}
await c.end();
```

Run after `vercel env pull .env.local`:
```bash
node --env-file=.env.local scripts/migrate.mjs
```

## Diagnostic instrumentation (drop-in)

When sign-in fails and you don't know which layer broke, add these prints to the Mobile auth repository. They tell you, in one round-trip, exactly where the chain snaps.

**Flutter (`auth_repository.dart`):**
```dart
import 'dart:convert';

Future<bool> signInWithGoogle() async {
  print('[GS] webClientIdLen=${_webClientId.length} '
      'serverClientId=${_google.serverClientId}');
  final account = await _google.signIn();
  if (account == null) { print('[GS] aborted'); return false; }
  print('[GS] email=${account.email} name=${account.displayName}');

  final auth = await account.authentication;
  final idToken = auth.idToken;
  print('[GS] idTokenLen=${idToken?.length ?? 0}');
  if (idToken == null || idToken.isEmpty) return false;

  // Decode JWT payload to see the aud claim
  final parts = idToken.split('.');
  if (parts.length == 3) {
    final json = utf8.decode(base64Url.decode(base64Url.normalize(parts[1])));
    print('[GS] payload=$json');
  }

  try {
    final res = await _dio.post('/auth/google', data: {'idToken': idToken, ...});
    print('[GS] backend status=${res.statusCode} body=${res.data}');
    ...
  } on DioException catch (e) {
    print('[GS] DioException status=${e.response?.statusCode} body=${e.response?.data}');
    rethrow;
  }
}
```

**Expo / React Native** — the equivalents:
```ts
import jwtDecode from 'jwt-decode';
const userInfo = await GoogleSignin.signIn();
console.log('[GS] idTokenLen', userInfo.idToken?.length);
console.log('[GS] payload', jwtDecode(userInfo.idToken!));
const res = await fetch(`${API}/auth/google`, { method: 'POST', body: JSON.stringify({ idToken: userInfo.idToken }) });
console.log('[GS] backend', res.status, await res.text());
```

What to compare:
- The `aud` claim printed from the decoded payload **must match** `process.env.GOOGLE_CLIENT_ID` on the backend, byte-for-byte. No quotes. No `\n`.
- The backend status. **401 with `Invalid Google idToken`** means audience mismatch (or signature/expiry, much rarer). **500** means something downstream failed — check `vercel logs` for the stack trace.

**Backend logs (Vercel):**
```bash
# In the backend repo:
vercel logs https://your-project.vercel.app
# Then trigger a sign-in attempt; the stack trace appears live.
```

The Vercel runtime logs MCP tool truncates messages — `vercel logs` from CLI gives the full stack trace (including the `expiresIn` / `audience` / `googleSub` error text).

## End-to-end verification flow (use after any change)

1. **Mobile build has the right Web Client ID baked in:**
   ```bash
   strings build/app/outputs/flutter-apk/app-debug.apk | grep apps.googleusercontent.com
   # Must show your Web Client ID, NOT the Android one.
   ```
2. **Installed APK SHA-1 matches a registered fingerprint:**
   ```bash
   adb pull "$(adb shell pm path com.your.pkg | head -1 | cut -d: -f2)" /tmp/installed.apk
   "$ANDROID_HOME/build-tools/<latest>/apksigner" verify --print-certs /tmp/installed.apk | grep "SHA-1 digest"
   # Must match one of the SHA-1s in google-services.json (or in Firebase Console).
   ```
3. **Backend env matches the Web Client ID:**
   ```bash
   vercel env pull .env.local --environment=production --yes
   set -a; source .env.local; set +a
   echo "len=${#GOOGLE_CLIENT_ID} value=$GOOGLE_CLIENT_ID"
   # len should be 72 (assuming standard Google client-id length); value plain.
   ```
4. **A real sign-in returns 201/200 + JWT:** trigger from device, watch backend logs and instrumentation prints.

## Setup-time checklist (new project)

In order, top to bottom:

1. **Create Firebase project** with Google as auth provider. Note the **project number**.
2. **Add Android app** with your `package_name` (e.g. `com.acme.app`). Don't add SHA-1s yet — add them in step 4 once you have all three keys.
3. **Generate the three keys:**
   - Debug keystore: shipped with the SDK at `~/.android/debug.keystore` (alias `androiddebugkey`, both passwords `android`).
   - Upload keystore: `keytool -genkey -v -keystore upload.keystore ...`. Store this in 1Password / a secure secret store. CI uses it to sign AABs.
   - Play App Signing: created by Google when you upload the first AAB to Play Console. Get its SHA-1 from Play Console → App integrity → App signing key certificate.
4. **Add all three SHA-1s to Firebase** Android app.
5. **Re-download `google-services.json`** (it's regenerated to include the SHA-1 list). Place at `android/app/google-services.json`. Gitignore it. Materialize from a CI secret on builds.
6. **Set up backend env** on Vercel: `GOOGLE_CLIENT_ID = <Web Client ID>` (Production scope). Use `printf '%s'` if scripted; paste **raw** (no quotes) if via the UI.
7. **Set up mobile build** to forward `GOOGLE_WEB_CLIENT_ID` to `--dart-define` (Flutter) or `expo.extra` (Expo) and on into `GoogleSignIn(serverClientId: ...)`.
8. **Verify with the diagnostic prints above.**
